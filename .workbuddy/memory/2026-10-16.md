## ⚠️ 重大纠正：WCH 中断属性规则（之前判断完全错误）

WCH 论坛官方明确:
> "V307 支持硬件与软件两种压栈方式,超过一定级数的压栈操作由软件完成,
> **不管使用哪种方式,都需要使用 attribute 对中断进行声明**。"

之前我判断"按键 ISR 优先级=3 走硬件压栈 → 不需要 attribute"是错的。
正确规则: **WCH 青稞 V4F 所有中断函数都必须用 attribute 声明**, 区别在于:
- 硬件压栈 → `__attribute__((interrupt("WCH-Interrupt-fast")))`
- 软件压栈 → `__attribute__((interrupt()))`  (注意是空字符串, 标准 GCC interrupt 属性)

不加 attribute 的后果(WCH 官方原话):
> "中断执行完成之后,中断执行之前保存的信息将不会被返回,中断会被认为
> 一个正常程序继续执行下去,但中断之后并没有程序,从而导致程序出现
> 类似跑飞状况。"

### CSR 0x804 = 0x0b 实际配置(已重新核算)
0x0b = 0b1011
- bit 0 = 1 → 硬件压栈使能
- bit 1 = 1 → 中断嵌套使能
- bit[3:2] = 0b10 = 2 → **4 级嵌套**(对应 NVIC_PriorityGroup_2)
- bit 4 = 0 → 关闭"硬件压栈溢出后中断使能"

### 4 级嵌套下软件/硬件压栈分配
4 级嵌套只有 4 个优先级档(0/1/2/3), 硬件堆栈深度 3 级:
- 优先级 0 → 软件压栈(1 级, 超出硬件 3 级深度的部分)
- 优先级 1/2/3 → 硬件压栈(3 级)

### 当前代码中断属性问题汇总

| ISR | 优先级 | 压栈方式 | 当前状态 | 正确做法 |
|-----|--------|---------|---------|---------|
| ADC1_2_IRQHandler | 0 | 软件 | ❌ 用了 WCH-Interrupt-fast | 改为 `__attribute__((interrupt()))` |
| EXTI0_IRQHandler | 3 | 硬件 | ❌ 没加 attribute | 加 `WCH-Interrupt-fast` |
| EXTI1_IRQHandler | 3 | 硬件 | ❌ 没加 attribute | 加 `WCH-Interrupt-fast` |
| EXTI15_10_IRQHandler | 3 | 硬件 | ❌ 没加 attribute | 加 `WCH-Interrupt-fast` |
| TIM3_IRQHandler | 3 | 硬件 | ❌ 没加 attribute | 加 `WCH-Interrupt-fast` |

### 用户现象: "按下按键没有进入中断" 的原因
按键 EXTI 中断没加 attribute → 中断返回用 ret 而非 mret → 中断状态恢复失败 → 程序跑飞或卡死 → 看起来像没进中断(实际第一次可能进了但跑飞)

### 修复方案(等用户确认)
1. key.c: 4 个按键 ISR 加 `__attribute__((interrupt("WCH-Interrupt-fast")))`
2. bldc.c: ADC1_2_IRQHandler 把 WCH-Interrupt-fast 改为 `__attribute__((interrupt()))`

## 已完成：ADC ISR 浮点上下文保护改造

### 改动文件
仅 `hardware/FOC/src/bldc.c` 一个文件。

### 改动内容
1. 抽出原 ADC1_2_IRQHandler 主体到 `static void ADC1_2_ISR_Body(void)`
2. ADC1_2_IRQHandler 改造为带浮点保护的版本：
   - RISC-V 平台（`#ifdef __riscv`）: 加 `__attribute__((interrupt("WCH-Interrupt-fast")))`
     + 144字节局部数组 fpu_save（16字节对齐）作为浮点寄存器保存区
     + 入口: 内联汇编用 fsw 保存 f0-f31 + frcsr + sw 保存 fcsr
     + 调用 ADC1_2_ISR_Body()（普通 C 函数, 由 gcc 管理通用寄存器栈帧）
     + 出口: 内联汇编用 flw + fscsr 恢复
   - 非 RISC-V 平台（`#else`）: 占位实现调用 ISR_Body, 仅用于 mingw64 语法检查
3. 不用 naked 属性, 让 gcc 完整管理 prologue/epilogue, 浮点保存区用局部数组 + `%[base]` 寄存器寻址, 避免与 gcc 栈管理冲突
4. t0 寄存器加入 clobber list（内联汇编用作临时寄存器）

### 设计考量
- 144字节 = 32×f(128) + fcsr(4) + 12对齐填充, 16字节对齐满足 RISC-V ABI
- 用 `%[base] "r"(fpu_save)` 让 gcc 自选基址寄存器, 两次内联汇编之间 gcc 可重选寄存器
- WCH-Interrupt-fast 让 gcc 生成 mret + 保存 callee-saved 通用寄存器
- ISR_Body 是普通 C 函数, gcc 自动管理它用到的 s0-s11/ra 栈帧

## 已完成：ISR属性改为标准GCC + ADC校准超时保护

### 问题现象
NVIC移到最后后，程序仍然到不了 while(1) 断点。

### 根因（两处）
**根因A：WCH-Interrupt-fast 属性导致跑飞**
- key.c 4个按键ISR用了 `__attribute__((interrupt("WCH-Interrupt-fast")))`
- 这是WCH定制GCC专有字符串，如果工具链版本不完美支持，ISR会被编译成普通函数
- 普通函数用 `ret` 返回而非 `mret`，中断状态没恢复 → 程序跑飞
- TIM3在Menu_Init()里就使能了（1ms周期），Menu_Init后1ms内就可能跑飞

**根因B：BLDC_ADC_CalibrateOffset 可能死循环**
- `while (ADC_GetFlagStatus(ADC1, ADC_FLAG_JEOC) == RESET)` 没有超时保护
- 切到软件触发模式后还 `ENABLE` 外部触发，可能导致软件触发不工作
- JEOC永远不置位 → 死循环 → 卡在BLDC_Init里

### 修复
**key.c**：`KEY_ISR` 宏从 `WCH-Interrupt-fast` 改为标准 `__attribute__((interrupt))`
- GCC标准属性，所有RISC-V GCC都支持
- 自动保存caller-saved通用寄存器 + 生成mret返回
- 硬件压栈的ISR用标准interrupt会多保存几个寄存器（与硬件保存重叠），但正确性有保证

**bldc.c**：
1. ADC ISR属性从 `interrupt()` 改为 `interrupt`（统一标准写法）
2. BLDC_ADC_CalibrateOffset：
   - `ADC_ExternalTrigInjectedConvCmd(ADC1, DISABLE)` 禁用外部触发
   - while循环加超时计数器（100000次），超时跳出
   - 校准失败用默认中点值2048兜底
   - valid计数器确保除零安全

## 已完成：ISR属性改回WCH专有格式（标准interrupt属性不工作）

### 问题现象
标准`__attribute__((interrupt))`和`__attribute__((interrupt()))`属性改完后程序仍然卡死，OpenOCD报`Failed to read memory (addr=0x20008000)`。

### OpenOCD诊断分析
- `misa=0x40901125` → 解码后F扩展存在，硬件浮点没问题
- 链接脚本：`RAM LENGTH=32K`，`__stack_size=2048`（2KB栈）
- 地址`0x20008000` = 0x20000000+0x8000 = SRAM边界外第一个无效地址
- 启动文件第300-301行：未处理的异常跳到`j 1b`无限循环
- SP跑飞到SRAM边界外 + 调试器无法读取内存 = CPU触发了异常进入默认死循环

### 根因
WCH定制GCC**不支持标准`__attribute__((interrupt))`和`__attribute__((interrupt()))`**（不带WCH专有字符串）。
这些属性被静默忽略 → ISR编译成普通函数 → 用`ret`而非`mret`返回 → mepc没恢复 → PC跑飞 → 触发异常 → 进入`j 1b`死循环。

### 修复（改回WCH专有格式）
**key.c**：`KEY_ISR` 宏改回 `__attribute__((interrupt("WCH-Interrupt-fast")))`（硬件压栈，优先级3）
**bldc.c**：ADC ISR属性改为 `__attribute__((interrupt("WCH-Interrupt")))`（软件压栈，优先级0）

注意：ADC ISR用`WCH-Interrupt`（不带fast），因为优先级0走软件压栈。

### 教训
WCH定制GCC只认自己的专有字符串`"WCH-Interrupt-fast"`和`"WCH-Interrupt"`，不认标准`interrupt`/`interrupt()`。mingw64语法检查走`#ifdef __riscv`的`#else`分支，无法发现这个问题。

## 已完成：OLED I2C卡死修复（卡在BYTE_TRANSMITTED）

### 问题现象
程序卡死在 `while (!I2C_CheckEvent(I2C1, I2C_EVENT_MASTER_BYTE_TRANSMITTED))`

### 根因
1. `I2C_CheckEvent`每次调用都读STAR2，数据发送阶段频繁读STAR2可能有副作用
2. `I2C_EVENT_MASTER_BYTE_TRANSMITTED`(0x00070084)要求BTF置位，BTF需要字节完全发送+收到ACK。OLED没响应(没接好/地址错/总线死锁)时BTF永不置位
3. 超时值0x10000(65536)太大，1024字节全屏数据每个字节都超时→整体约2-3秒，表现为"卡死"
4. 超时后只break继续发下一字节，没发STOP复位总线，状态一直异常

### 修复（oled.c）
1. 新增`OLED_I2C_BusReset()`：上电时GPIO方式给9个时钟脉冲释放死锁从机+产生STOP
2. `OLED_I2C_Init()`加总线恢复+I2C软件复位(`I2C_SoftwareResetCmd`)
3. `OLED_I2C_Write()`改用分步单标志检查(不用`I2C_CheckEvent`组合事件):
   - SB标志→地址→ADDR标志→读SR1+SR2清除→TXE标志→写DR→...→最后BTF→STOP
4. 超时值从0x10000改为10000(约0.7ms，快速失败)
5. 错误时goto发STOP+软件复位，让总线恢复可用
